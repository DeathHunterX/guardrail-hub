# ZAP Worker Pool Architecture

## Status

Implemented (`mcp-server/app/integrations/owasp_zap/`, `mcp-server/app/services/tools/owasp_zap/`, `mcp-server/app/services/tools/owasp_zap/worker/`). This document set describes the code as it exists, not a proposal.

## Why this exists

The original ZAP pool generated worker addresses from a configurable prefix and a count (`ZAP_CONTAINER_NAME_PREFIX` + `ZAP_AMOUNT_OF_CONTAINERS`, producing `http://<prefix>-1`, `http://<prefix>-2`, ...). That only works when the number of workers is fixed and known at server-configuration time, which breaks down for:

* **Dynamic scaling** — `docker compose up --scale zap=N` starting/stopping replicas at runtime.
* **Self-hosted deployments** — an operator's own worker count/topology, not ours to assume.
* **Future Kubernetes compatibility** — pods don't have predictable sequential hostnames.

The replacement: **every ZAP worker announces itself.** The server never generates a worker address; it only ever uses what a worker told it.

## What changed, in one paragraph

A worker used to be `prefix-{index}`, generated by the server from two config values, with an in-memory dict of container-name → busy/idle. Now a worker is whatever registered itself — a `worker_id`, `hostname`, `endpoint`, and `port` it reported — held in an in-memory Registry keyed by that self-reported `worker_id`, kept alive by periodic heartbeats, and reaped (marked Offline) if heartbeats stop. Busy/idle is derived from whether an `op_id` is attached, never tracked as a separate flag. A Round Robin Scheduler (an isolated, replaceable strategy) picks who runs the next operation from among Active + idle workers. The operation queue itself was moved out of memory entirely: a scan request is persisted as `status=QUEUED` in the Operations table the moment it's submitted, and a background Dispatcher polls that table (oldest first), assigns queued rows to idle workers, and only then executes the scan — so a `QUEUED` request survives an mcp-server restart untouched (see [sequence-diagrams.md](sequence-diagrams.md) for the one known edge case this doesn't cover: a row already `RUNNING` at the exact moment mcp-server itself crashes).

## Non-goals

* This is not a distributed scheduler — the Registry and Dispatcher are in-process, single-mcp-server-instance state. Running multiple mcp-server replicas against the same Postgres/DynamoDB backend would need a real distributed lock or leader election for the dispatcher loop; that's out of scope here.
* Worker Registry state is *not* persisted. Workers are ephemeral and re-register on every start, so registry state naturally rebuilds itself after an mcp-server restart. What must survive a restart — queued work — lives in the Operations table instead (see [database-map.md](../../.ai/intelligence/database-map.md)).
* An operation that was `RUNNING` at the exact instant mcp-server itself (not the worker) crashes is left `RUNNING` rather than auto-failed or auto-resumed — see the "Known gap" in [sequence-diagrams.md](sequence-diagrams.md).
